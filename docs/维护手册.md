# BiliYTPlayer 维护手册

## 一、开工 SOP（每次改代码前必做）

**一句话启动存档**：对 AI 说「先帮我提交存档」。

AI 应执行：

```bash
cd C:/Users/Administrator/WorkBuddy/重置版
git add -A && git commit -m "存档：<一句话说明当前状态>"
```

规则：
- 一次会话只提**一个**需求，不说"顺便把那个也改了"
- 每次需求开工前都先存档，改崩了随时 `git reset --hard HEAD~1` 回到上一个存档点
- 查看历史存档：`git log --oneline`；查看某次存档改了什么：`git show <编号>`

## 五、红线：踩坑记录（改这些地方前必读）

这些知识是花了真金白银的调试时间换来的，**注释里也标了"实测"，删代码时不要连带删掉**：

1. **音轨挂载**：`audio-file` 是 mpv CLI 选项，不是可写 property——运行时挂音轨唯一有效途径是 `audio-add <url> select`（auto 不选中会哑剧），且 `loadfile` 后必须等 ~1 秒再挂。
2. **自动连播**：`keep-open=yes` 会抑制 `end-file` 事件，必须 `observe_property('eof-reached')`；end-file 仅作兜底。
3. **切集快捷键**：`Ctrl+←/Ctrl+→`，刻意避开小键盘数字键（mpv 默认绑定数字 seek）。
4. **代理**：系统代理当前是 `127.0.0.1:52459`（曾经是 52460，代理工具换过端口；代码靠 `_resolve_proxy_url` 自动探测，别写死）；mpv 不读环境变量，必须在启动参数显式传 `--http-proxy` 和 `--ytdl-raw-options proxy=`。
5. **mpv 配置**：只改 `mpv-portable/portable_config/mpv.conf`，**禁止改 Python 源码**里的渲染参数；改完静默保存。
6. **流优先级**：同分辨率下**码率(bandwidth)优先**，编码权重 `{13:3, 12:2, 7:1}` 仅作码率接近时的决胜手（AV1>HEVC>AVC）。2026-10-22 实测：B 站给 4K AVC 的码率是 AV1 的 2.2~3.3 倍，AV1 效率优势补不回码率差，码率优先=画质最高。别再改回编码绝对优先。
7. **B 站 API**：裸 socket `_FastBiliSession` 直连，绕过 requests/urllib3 的代理探测延迟——别"顺手优化"回 requests。
8. **架构纪律**：在能跑的房子里装修（精简合并），不做推倒重写。
9. **YouTube 限流（2026-10-19 踩坑）**：代理出口 IP 被 YouTube 标记时，默认 client（android_vr）的播放地址被 CDN 锁死——只放行每个 URL 的前 ~2.5MB，mpv 必 403（窗口一闪即逝）。应对：`launch_player` 播放前会做一次中段 Range 探测，判定限流就自动切 `player_client=android`（地址不受限，代价是最高 360p）。换代理节点可能解除限流、恢复高画质，无需改代码。
10. **mpv.conf 的 profile 陷阱（2026-10-19 踩坑，曾致自动连播失效）**：mpv.conf 里 `[xxx]` 是 profile 段头，**其后的选项全部归属该 profile，直到下一个 `[ ]` 头——没有"退回全局"的语法**。曾因把全局选项写在 `[HLG]` 后面，导致 `cache`/`hwdec`/`keep-open`/`ao=wasapi` 等一大片设置只对 HLG 片源生效，普通视频全是默认值（`keep-open` 失效 → 播完直接退出 → 连播来不及切）。铁律：**全局选项一律放文件上方，条件 profile 一律放最后**。改完用 IPC 查属性验证：`get_property keep-open` 应为 `true`。
11. **番剧必须走 PGC API（2026-10-19 修复）**：视频 API（`/x/player/wbi/playurl`）对番剧一律返回 `code=-404`，必须用 `/pgc/player/web/playurl`（`get_playurl_pgc`）。免费账号只返渐进式 `durl`（单文件混合流，`pick_streams_from_result` 已兼容 dash/durl 两种形态），大会员才有 DASH。另：`keep-open-pause=no` 是自动连播续播的前提（EOF 暂停态会被 loadfile 的新文件继承，卡在暂停）。
12. **扫码窗：wait_window 期间子线程绝不许碰 tkinter（2026-10-27 实测）**：tkinter 的 C 层要求「主线程正处在 main loop 中」才允许注册回调，而 `wait_window` 走的是 Tcl 层的 `tkwait` 命令，C 层的 `dispatching` 标志仍是 0。于是子线程调 `after` 会先卡 1 秒再抛 `RuntimeError: main thread is not in main loop`。危害链：**二维码画不出（空白框）→ 状态栏卡在「正在获取二维码…」→ finally 的关窗 after 同样丢失 → wait_window 永久假死**。这个雷只在**冷启动**炸（那时 mainloop 还没起来），热路径「重新登录」恰在 mainloop 内所以长期没暴露。架构：**子线程只往 `queue` 投纯 Python 数据，一切 tkinter 操作交给主线程的 `drain` 轮询（50ms）代劳**；用户点取消后线程迟迟不醒（网络请求最长 10s + 轮询 2s）时，由 `drain` 在 1.5s 后强制收尾。回归脚本：mock 三场景 + 真网络探针 5/5。
13. **mpv 生命周期与 IPC 管道（2026-10-30 修，B-4）**：关软件不关 mpv 是**有意设计**（复制链接后可以关掉工具继续看片），所以每次起播前都要清退旧实例，孤儿是常态不是意外。清退三步：IPC quit（优雅，会释放 WASAPI 独占音频设备）→ 等管道释放（4s）→ 仍被占则强杀。**强杀只杀路径等于本软件播放器的 mpv**，用户自己装的独立 mpv（同名 mpv.exe 装在别处）不受牵连。起播后必须验证管道真建立（`_wait_pipe_ready`）——管道没建立时画面照常播放，但切集 / 自动连播 / 鼠标交互全废，用户毫无察觉；这种「看着正常其实残废」的状态必须提示，不能无声继续。回归：`tests/e2e_mpv_lifecycle.py`（会 taskkill 掉系统里所有 mpv，别边看片边跑）。
14. **input.conf 禁绑脚本接管的键（2026-10-27 补）**：`RIGHT` / `MBTN_LEFT` / `MBTN_LEFT_DBL` 由 `scripts/click-handler.lua` 接管（单击暂停/双击全屏/→短按快进/长按倍速）。mpv 的派发规则：input.conf 一旦绑定同键，**脚本的复杂绑定被完全屏蔽**（长按倍速静默失效）；反之若两边都触发则双发（单击暂停变"暂停-恢复"空转）。input.conf 里这三个键的位置只能放注释，不能放绑定。改完跑 `legacy/tests/e2e_interaction.py` 验证（首测 2026-10-27，8/8 PASS）。
